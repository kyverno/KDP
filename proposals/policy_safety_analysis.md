# Overview
[overview]: #overview

A Kyverno policy is accepted when it is structurally valid. Its runtime safety, and whether it matches the author's intent, are not checked and surface only at enforcement time. This proposal adds Policy Safety Analysis: static analysis of the policy itself (not the workloads it governs) that detects dangerous and silently-ineffective policies before they enforce. It reports policies that can block cluster recovery, policies whose scoping has no effect, policies whose autogenerated form drops a mutation, policies that conflict with each other, and it can preview a policy's effect against a live cluster before the policy is enforced. The analysis is delivered through three surfaces: admission warnings at policy creation, a CLI command for use in CI, and an opt-in pre-enforcement impact preview.

# Definitions
[definitions]: #definitions

- **Footgun**: a policy that is structurally valid and accepted, but whose behavior is dangerous or silently incorrect.
- **failurePolicy / fail-closed**: a webhook setting of `Fail` means the API server rejects a request when the webhook is unreachable. A fail-closed policy matching resources the cluster needs to boot can block the cluster from recovering.
- **Cluster-scoped resource**: a resource that does not live in a namespace (for example `Node`, `CertificateSigningRequest`, `CustomResourceDefinition`). A `namespaceSelector` has no effect on these.
- **Autogen**: automatic generation of pod-controller rules (Deployment, StatefulSet, Job, CronJob, and others) from a policy written against `Pod`, so the same intent applies to workloads created through controllers.
- **Match condition**: a CEL expression on a policy that decides whether the policy applies to a request.
- **Blast radius / impact**: the set of already-running resources that a not-yet-enforced policy would newly reject or mutate if enforced.
- **Static analysis**: inspecting a policy without executing it against live traffic, using only the policy definition (and, for impact analysis, the cluster's current inventory).

# Motivation
[motivation]: #motivation

Kyverno checks that a policy is well-formed. It does not check that a policy is safe to run. That gap produces several distinct, recurring failure classes, each of which is determinable before enforcement from the policy definition alone.

- **Fail-closed policy on cluster-scoped bootstrap resources can block cluster recovery.** After a full restart, the API server rejects requests for resources a node needs to register, the controller that owns the webhook cannot start, and the stale webhook is never repaired. Determinable from the policy: `failurePolicy: Fail` plus a matched cluster-scoped resource.
- **`namespaceSelector` has no effect on cluster-scoped resources.** A policy scoped this way applies more broadly than intended, or an intended exclusion is ignored. Determinable from the policy: a `namespaceSelector` present together with a matched cluster-scoped resource.
- **Autogen does not rewrite every field for the controller form.** A mutation that is correct on a bare `Pod` can be a no-op on a `Deployment`, with no error. Determinable: compare the autogen output against the source rule.
- **Policies are evaluated independently and intent is not reconciled across them.** Two mutations can overwrite the same field (last-writer-wins), or one policy can mutate a resource into a shape another policy then rejects. Determinable by composing the policy set over representative inputs.
- **There is no pre-enforcement impact check.** An author cannot determine which already-running resources a policy would newly reject or mutate before enabling enforcement. Determinable by evaluating the candidate policy against the current inventory.

Use cases: an author gets immediate feedback on a dangerous policy at `kubectl apply`; a platform team blocks a cluster-wedging policy in a pull request before it reaches any cluster; an operator previews a policy's effect on running workloads before switching it to enforce.

Expected outcome: the most damaging policy-mistake classes are caught at authoring time, in CI, and at apply time, instead of at runtime.

# Proposal
[proposal]: #proposal

Add a Policy Safety Analysis engine: a library that takes a policy (or a set of policies, optionally with a cluster snapshot) and returns findings. Each finding carries a stable rule identifier, a severity, a location in the policy, and an explanation. The same engine powers three surfaces, delivered in three phases.

**Phase 1: author-time safety lint, surfaced as admission warnings.** When a policy is created or updated, the analyzer runs the single-policy checks and returns warnings alongside the existing acceptance of the policy. The policy is still admitted (warnings, not rejections, so the analyzer never blocks an advanced use case), and `kubectl apply` prints, for example:

```
Warning: [KS001] rule "deny-privileged" uses failurePolicy: Fail and matches the
  cluster-scoped resource Node. A namespaceSelector cannot exclude it. If Kyverno is
  unavailable, this rule can block node registration and prevent cluster recovery.
Warning: [KS010] namespaceSelector on rule "restrict-images" has no effect because
  the matched resource ClusterRole is cluster-scoped; the selector is ignored.
Warning: [KS020] this MutatingPolicy is autogen-eligible, but mutation #2 uses a
  JSONPatch that references object.spec.containers; that path is not rewritten for
  controllers, so the mutation will not apply to Deployments/StatefulSets/etc.
```

Phase 1 ships a first set of high-value, low-false-positive rules: fail-closed on cluster-scoped/bootstrap resources; ineffective `namespaceSelector` on cluster-scoped resources; autogen that drops a mutation or variable; and constant or type-unsatisfiable match conditions (only the cases decidable from the type-checked expression).

**Phase 2: `kyverno lint` and a CI gate.** The same engine is exposed as a CLI command that analyzes policy files offline, with no cluster, across a whole directory at once. It produces machine-readable output (the existing report schema and/or SARIF) and a non-zero exit code when findings exceed a configurable severity, so a team can block a pull request that introduces a dangerous policy before it is applied. This is the shift-left surface: policies are caught in review, not in the cluster.

**Phase 3: cross-policy and cluster-aware analysis.** Two analyses that need more than a single policy in isolation:
- Conflict detection takes the whole policy set and reports where two mutations write the same field, where one policy's mutation output would be rejected by another policy's validation, or where generate targets collide. Because a mutation is a function of its input, this is best-effort over the resources the user supplies or the cluster provides, and findings are reported as "can conflict for inputs like X," not as a soundness proof.
- Impact preview takes a candidate, not-yet-applied policy plus the cluster's current inventory and reports the blast radius: how many running resources would newly fail validation and how many would be mutated, with examples. It reuses the existing engine and live-resource enumeration, adding only the "treat this as not yet applied and report the newly-affected set" framing.

For existing users the change is additive: they author policies as before and start seeing warnings. For new users it removes the main source of early confusion, which is the absence of any signal when a policy is misconfigured.

# Implementation
[implementation]: #implementation

The analysis engine is a new package that consumes the policy types and returns structured findings. Each finding carries a stable rule ID (so it can be suppressed or referenced), a severity, a location, and a message. Rules are independent and registered into the engine, so the catalog grows without changing the surfaces.

Phase 1 reuses three pieces of existing machinery, which is why the author-time surface needs little new plumbing:

1. The warning channel is already wired. Each policy type's `Validate` function returns `([]string, error)`, and the policy webhook handler forwards those warnings to the API server, which prints them on `kubectl apply` (`pkg/webhooks/policy/handlers.go`, where `warnings, err := <type>validation.Validate(...)` flows into `admissionutils.Response(uid, err, warnings...)`). The analyzer's findings join this existing return path. No new admission wiring and no new CRD.

2. Static inspection of CEL without executing it is already done in-tree. The HTTP-usage check walks a compiled expression's AST to find an identifier, using `celast.NavigateAST(ast.NativeRep())` and `celast.MatchDescendants` (`pkg/cel/compiler/http.go`). The analyzer uses the same walk to recognize constant and type-unsatisfiable conditions, and the compiler already exposes the type information (`ast.OutputType()`) needed to do this soundly for the decidable cases. Recompiling a policy purely to produce diagnostics is already the pattern (`pkg/cel/policies/*/validate.go`; a helper already enumerates every CEL expression in a policy).

3. Scope, failurePolicy, selectors, and autogen output are all derivable before deployment. The webhook layer already determines, from the policy alone, the resource scope and whether a `namespaceSelector` applies. Autogen is a pure function returning the generated rules (`pkg/cel/policies/*/autogen`), so the "autogen drops this field" check runs by calling autogen and comparing what was and was not rewritten, with no cluster.

Phase 2 wraps the same engine in a `kyverno lint` command that loads policy files (the CLI already loads every policy type), runs the engine, and renders findings plus an exit code. Output reuses the existing report result schema so existing consumers can read it, and adds a SARIF renderer for code-review tooling.

Phase 3 builds two harnesses on the existing engines. Conflict analysis drives the existing mutate pipeline to chain one policy's patched output into the next policy and into validation, then diffs the outcomes; the engines already run headlessly against a fake client in the CLI. Impact preview reuses the CLI `--cluster` resource enumeration (which already fetches the resources a policy matches) and the existing engine, adding the baseline-versus-candidate diff that turns absolute results into a newly-affected set, and emits the result as a report.

# Migration (OPTIONAL)
[migration]: #migration

None. The feature is additive and opt-in. Phase 1 emits warnings only and never changes whether a policy is accepted, so no existing policy behavior changes. The CLI command and the impact preview are new, separate surfaces. There are no breaking API changes.

# Drawbacks
[drawbacks]: #drawbacks

- False positives reduce trust. A check that warns on a legitimate advanced policy trains authors to ignore warnings. Mitigated by shipping only high-confidence rules first, keeping every finding warning-level (never a rejection), and giving each rule a stable ID that can be suppressed.
- Some analyses cannot be sound. Detecting that an arbitrary CEL condition is always true, or that two mutations always conflict, is undecidable in general because behavior depends on the input. The proposal scopes these to decidable, type-level cases and to best-effort, input-driven reporting, and states that limit in the output.
- Maintenance surface. A rule catalog is ongoing work and must track new policy features. Keeping rules independent and registered limits the cost of each addition.
- Impact preview has an operational cost. Enumerating every resource a broad policy could match in a large cluster has memory, latency, and RBAC implications. It is opt-in and the lowest-priority phase.

# Alternatives
[alternatives]: #alternatives

- Do nothing and fix each footgun reactively. The status quo addresses each dangerous policy class with a separate runtime flag or bug fix after users are affected. That leaves the author with no general, before-the-fact signal and re-pays the cost for every new footgun class. A single analysis engine generalizes the prevention.
- Per-check, runtime-only warnings. A specific warning for one dangerous shape (for example an over-broad wildcard policy) is a single admission event for a single policy. It cannot express cross-policy conflicts, cannot run offline in CI, and grows into an unmanaged set of one-off checks. This proposal gives those checks a shared engine, a severity model, and common surfaces.
- Rely only on audit mode. Audit mode reports what already broke after enforcement begins. It does not prevent a cluster-wedging policy from being applied and offers no authoring-time or pull-request-time signal.
- A third-party external linter. A separate tool cannot reuse the engine's own compilation, autogen, scope resolution, and report schema, so it drifts from Kyverno's actual behavior. Owning the analysis inside Kyverno keeps it correct by construction.

Impact of not doing this: the most damaging policy mistakes (cluster-wedging fail-closed rules, ineffective scoping, silently-dropped mutations, conflicting policies) continue to be found at runtime, and new users continue to spend their first effort debugging the absence of a signal.

# Prior Art
[prior-art]: #prior-art

An early request to detect and prevent obvious policy problems was narrowed to a single shipped check (rejecting self-referential generate loops); the general capability was never built. Adjacent in-flight work warns at admission time about over-broad wildcard policies; this proposal is the engine such a check plugs into. A request to catch policy footguns before apply, and to report how many cluster resources a policy matches in a pull request, is open and unanswered.

In the wider ecosystem, workload scanners (KubeLinter, kube-score, Polaris, Checkov, Trivy, Kubescape) lint the workload against policies; none analyzes the policy for safety. Gatekeeper offers fixture testing, a narrow internal mutator schema-conflict guard, and post-deployment dry-run via its audit controller; it does not provide author-time semantic footgun linting, general cross-policy conflict detection, or pre-deployment cluster-aware impact preview. Kubewarden policies are WebAssembly, which makes static analysis of the policy impractical, and its audit-scanner is a post-deployment scan of existing resources. Author-time analysis of the policy as the subject is unclaimed across these tools.

# Unresolved Questions
[unresolved-questions]: #unresolved-questions

- To resolve before merge: the initial Phase 1 rule set and each rule's severity; the finding identifier scheme and how suppression is expressed (annotation versus configuration); whether the analyzer is always on or gated behind a flag.
- To resolve during implementation: which CEL constant and unsatisfiable cases are caught soundly versus deferred; the conflict-detection input strategy (user-supplied, sampled, or cluster-provided resources); the output rendering details (report schema fields and SARIF mapping).
- Out of scope for this KDP (possible future, independent work): automated progressive rollout (canary, audit-to-enforce promotion, auto-rollback on a violation spike); a browser or IDE authoring assistant; runtime enforcement-lifecycle guarantees during controller startup and restart, which is the runtime counterpart to this author-time prevention and deserves its own design.

# CRD Changes (OPTIONAL)
[crd-changes]: #crd-changes

None required. The feature reads existing policy types and emits warnings, CLI output, and reports using existing schemas. Suppression of individual findings, if pursued, would use policy annotations rather than a CRD change.
